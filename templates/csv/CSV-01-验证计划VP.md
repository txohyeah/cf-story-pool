## 1 目的与范围

### 1.1 目的

本计划规定本机构 CTMS（临床试验管理系统）计算机化系统验证的**范围、策略、深度、职责、进度、判定规则与批准条件**，用于答复以下法规要求：

- 新版 GCP 第五十三条（三）：通过可靠的系统验证，符合预期用途和预先设置的技术性能，并保证在整个试验过程中系统始终处于验证有效的状态；
- 新版 GCP 第五十三条（四）：定期审查系统运行情况，对发现的问题进行评估并采取相应措施；
- 《药物临床试验计算机化系统和电子数据指导原则》"验证"一节：以用户需求为起点，经设计、试验特定配置、需求可追溯性、测试计划与执行，验证报告经批准后方可发布；
- 《药物临床试验机构监督检查要点及判定原则》★A1.8：验证与确认资料、培训、定期审查与处理问题。

### 1.3 不纳入范围（划界，非"不做"）

| 不纳入项 | 理由与替代处置 |
|---|---|
|  Electronic Data Capture（EDC）意义上的数据采集、随机表生成与中心化随机化（IWRS/IRT） | 本平台定位为机构侧管理系统，不承担方案规定的数据管理与随机化职能；随机表与盲底作为外部输入归档并做可追溯性验证，其生成过程不在本验证范围内（对应 `URS-B5-14`）。 |
| 基础设施高可用与容灾切换 | 属机构信息化基础设施投资范围，本验证仅确认"备份可恢复 + 数据可读"，不承诺切换时长；相关配置要求见方案第十二章与附录 E。 |
| 第三方 CA 数字证书服务 | 现阶段电子签名为平台内置签名提供方（内容哈希绑定 + 手写签名档），未接入第三方 CA；接入后以独立变更单触发再验证（`URS-A7-06`、CSV-13 第 5 章）。 |
| Ⅰ期临床病室采集与床旁终端能力 | 属独立产品线，不在本次交付与验证范围内。 |
| 技术演进方向项（轨迹链式存证、异常模式识别、云端共享验证责任模型） | 方案 6.8 列为中长期版本方向，不进入本期验收判据。 |

**划界纪律**：上表任何一项在验收报告中不得被隐式视为通过；凡属"由机构或第三方承担"的条件（时间源、备份作业、接口改造、等级保护测评），CSV-12 逐项列明交付状态与责任方。

## 3 验证策略

### 3.1 三条基本判断

1. **验证不是一次性上线动作。** "始终处于验证有效"是运行期义务，因此本计划把 CSV-13（变更即再验证）与 CSV-15（年度验证回顾）列为计划的一部分，而非上线后的补充动作。
2. **预期用途由机构定义。** URS 由机构各业务域（组织管理部门、伦理委员会、药房、资料/档案、信息科、财务）分别确认自己那部分并批准；我方不得以产品功能清单替代机构需求清单。
3. **范围与程度基于风险。** 不做"全功能全量验证"这类不可执行的承诺；以功能对受试者权益、数据完整性、合规证据的影响程度决定测试深度（第 5 章）。

### 3.2 生命周期模型

采用 V 模型并以指导原则的骨架落地，左端从需求出发、右端从环境确认回到追溯：

```
URS（CSV-02）          ←——可追溯性——→   验证报告（CSV-12）
  │                                            ▲
  ├─ 功能规格 FS（CSV-03）     ←——→  运行确认 OQ（CSV-07）／性能确认（CSV-08）／流程确认 PQ（CSV-09）
  ├─ 技术规格 TS（CSV-03）     ←——→  安装确认 IQ（CSV-06）
  ├─ 配置说明（CSV-04）        ←——→  集成验证（CSV-10）
  └─ 风险分级（本计划第 5 章）  ←——→  测试深度与用例配置（各确认方案）
```

### 3.3 测试计划四要素（每条用例的必备声明）

指导原则要求测试计划含**测试项、测试环境、验收标准、测试数据**四要素。本体系将其细化为用例表的列：

| 列 | 要求 |
|---|---|
| 用例号 | `TC-IQ/OQ/PF/PQ/IV-nn`，一经分配不复用 |
| 覆盖 URS | 至少一个 URS 编号；追溯不到 URS 的用例不得存在 |
| 用例类型 | 正向 / 负向 / 边界 / 依赖外部 |
| 前置条件 | 环境标识、账号所属角色（不写账号名）、数据类别 |
| 步骤 | 可被第三人照做复现的操作序列，页面路径写到出口级 |
| 预期结果 | 唯一可判真假表述；负向用例的预期结果必须是"系统拒绝 + 提示语 + 留痕位置" |
| 实际结果 | 执行时填写 |
| 结论 | 通过 / 未通过 / 偏差（挂 `DEV-` 号） |
| 证据 | `EV-` 号（导出件、脚本输出、签署件），非必需不用截图 |

### 3.4 负向用例是必选项，不是附加项

高风险面的合规性主要由"系统会不会拒绝不该发生的操作"来证明。以下负向面必须显式设计用例并通过（判据统一为**被拒绝且留痕**）：

| 负向面 | 拒绝证据的落点 |
|---|---|
| 越权访问（功能码缺失、数据档位之外、跨院区） | 接口业务码拒绝 + 稽查轨迹 |
| 共享账号／非本人操作 | 签署资格校验拒绝 + 待办归属留痕 |
| 缺手写签名档的签署 | 签署动作拒绝 + 提示 |
| 未达会签阈值的推进 | 推进闸拦截并点名欠签者 |
| 重复提交／并发签署 | 幂等守卫拒绝二次落行 |
| 办结后撤换已消费递交件 | 封口闸拒绝 + 台账可查 |
| 引用未批准或已停用版本的知情同意书 | 版本硬校验拒绝 |
| 盲态下访问盲底、申请人自批揭盲 | 揭盲双人审批闸拒绝 |
| 无权限导出／导出含未脱敏身份 | 导出动作留痕 + 响应级脱敏 |

### 3.5 自动化对账口作为证据来源

系统内已有的静态与运行时对账能力（权限覆盖率、数据级接线覆盖率、授权矩阵与签名链冒烟、版本链与流程链冒烟、配置包一致性校验、前端类型检查、系统资源台账、配置体检页）直接产出证据件，登记命令与执行时间即可，不重复人工誊抄。可用入口清单见 `docs/csv/README.md` 第九节。

**纪律**：自动化输出是证据来源，不替代用例。任何"绿灯"结论前须确认对账脚本未中途抛错——中途失败会让计数显示为 0 项，形成假绿灯。

## 4 组织与职责（RACI）

R=执行，A=批准，C=协作，I=知会。**验证报告与流程确认（PQ）的批准权在机构**，这是"使用方对验证结果进行确认"的制度体现。

|---|---|---|---|---|---|
| 验证计划编制与批准 | R | A | A | C | I |
| URS 编写与批准 | C | A | C | R（各自域） | I |
| 基线测量（现状数据） | C（提供模板） | A | C | R | I |
| 规格说明 FS/TS | R/A | C | C | C | I |

| 测试用例设计 | R | C | C | C | I |
| IQ 执行 | R | I | A | I | I |
| OQ 执行 | R | C | C | C | I |
| 性能确认执行 | R | I | A | I | I |
| PQ 执行 | C（支持） | A | I | R（关键用户） | I |
| 集成验证 | R | I | A | I | C（数据映射确认） |

## 5 风险分级与测试深度

### 5.1 分级判据与最低用例配置

与 `docs/csv/README.md` 第六节一致：

| 风险级 | 判据 | 最低用例配置 |
|---|---|---|
| 高 | 涉及试验参与者权益与身份、数据完整性、权限裁剪、电子签名与校验、稽查轨迹、编号唯一性、流程推进闸、盲态与揭盲、材料封口与撤换、经费结算闸 | 正向 ≥1、负向 ≥1、边界 ≥1；负向以"系统拒绝 + 留痕"为通过判据 |
| 中 | 计算与规则类：字段校验与显隐、清单齐备性、超窗计算、库存对账、拆账与预警、保留年限 | 关键规则用例 ≥2（含一个边界值）+ 抽样回归 |
| 低 | 展示、筛选、排序、导出格式、工作台卡片、门户内容 | 冒烟 1 条 + 目视确认记录 |
| 外部依赖 | 文档转换与水印、院内接口、备份作业、时间源、CA | ≥3 条：失败不破坏业务动作、可重跑且幂等、过程有留痕 |

### 5.2 高风险面清单（用例设计的强制覆盖对象）

| 序号 | 高风险面 | 关联 URS | 定级理由 |
|---|---|---|---|
| H1 | 功能码与写接口鉴权（每个写接口都要码，裸写必须为 0） | `URS-A1-01`、`URS-A1-06` | 权限失控直接影响数据真实性与责任归属 |
| H2 | 数据范围档位与服务端二次拒绝 | `URS-A1-02` | 越权读取即个人信息外泄 |
| H3 | 项目授权分工表与行级/整表签署、到期扫描 | `URS-A1-03` | 授权链是 GCP 责任划分的证据基座 |
| H4 | 一人一账号强制与临时受控授权（替代共享账号） | `URS-A1-04`、`URS-A1-05` | 共享账号即签名不可信 |
| H5 | 稽查轨迹：前后值捕获、不可关闭、脱敏、导出 | `URS-A6-01`—`URS-A6-05` | 数据完整性与可追溯性的核心 |
| H6 | 电子签名：内容哈希绑定、可校验、手写签名档强制、撤销留痕不删行 | `URS-A7-01`—`URS-A7-05` | 签名即法律效果 |
| H7 | 跨端手写签名接力的一次性令牌 | `URS-A7-04` | 令牌可复用即身份冒用 |

| H10 | 驳回重发保留原填写与原判定痕迹 | `URS-A2-04` | 覆盖历史即破坏 ALCOA 可追溯 |
| H11 | 材料清单双轴（齐备性/符合性互不覆盖）与判定留痕 | `URS-A3-04`、`URS-B1-03` | 人工判定被系统态覆盖即失真 |
| H12 | 办结封口、已消费件禁撤换、撤销解锁与跨轮继续锁 | `URS-B7-07` | 递交证据一旦被替换即不可信 |
| H13 | 试验参与者身份分离存储、鉴认代码、响应级脱敏 | `URS-B5-01`、`URS-B5-02` | 权益与隐私红线 |
| H14 | 知情同意版本与被批准版本硬校验、六类同意留痕 | `URS-B5-03` | 直接关系受试者权益 |
| H15 | 访视超窗检测与原因无条件落库 | `URS-B5-07` | 方案偏离的证据链 |
| H16 | 揭盲双人审批与盲底访问控制 | `URS-B5-13` | 盲态破坏不可逆 |
| H17 | 编号引擎唯一性与节点动态取号 | `URS-A5-01`、`URS-A5-02` | 编号重复即文书失效 |
| H18 | 归档只读与三类保留年限、逻辑删除不可物理绕过 | `URS-A8-01`、`URS-A8-02` | 保存义务 |
| H19 | 更正流程（原值不覆盖、原因时间人员自动记录） | `URS-A8-03` | 数据修正必须留痕 |
| H20 | 经费结算闸与拆账口径（谁点按钮不得决定系统算出的数） | `URS-B4-07`、`URS-B4-02` | 计算被权限反向影响 |
| H21 | 药房账实对账与 FEFO、批次追溯到人 | `URS-B6-05`、`URS-B6-04` | 用药安全 |

| H23 | 权限季度审查与账号生命周期一致性 | `URS-A1-07` | 运行期持续合规 |

### 5.3 中风险面（举例，完整清单见 CSV-02 风险级列）

表单字段级校验与条件显隐、变体挂靠解析、跨阶段数据复用的来源与版本标注、材料齐备性计算、跟踪审查到期生成、超窗窗口与周期计算、库存三级数量与效期、拆账比例与预警线触发、保留年限计算、待办物化与阶段衔接生成、水印文字取数。

### 5.4 低风险面

列表筛选与排序、导出格式与列名、工作台卡片展示、门户内容区块渲染、提示语与文案、颜色与版式基线（列表版式属"目视确认 + 宽度实测"类，不作为合规判据）。

### 5.5 依赖外部面与判据

## 7 测试环境与测试数据

### 7.1 环境

- 用于 OQ/PQ/性能/集成验证的环境须与生产**同构**：应用版本、依赖版本、数据库版本与关键参数、时区与时间源、配置快照、外部依赖的三态开关取值。
- 环境差异由 IQ 记录，每项差异必须写"差异说明 + 对结论的影响"；影响不可判断时按"结论不适用"处理并安排补测。
- 性能确认须在**与生产同等规格**的环境执行；在低配环境测得的数字不得作为生产结论。
- 环境标识（实例名或部署编号）在执行记录中必填，使证据可回放。

### 7.2 数据

三类测试数据逐用例声明（对应 `README.md` 第七节）：

| 类别 | 定义 | 使用要求 |
|---|---|---|
| `D-夹具` | 可重复预制数据 | 用例声明夹具集；夹具变更须同步影响该集的用例 |
| `D-造数` | 执行时现场构造的一次性数据 | 记录造数步骤；不得依赖"演示库里已经有"这一隐式状态 |
| `D-脱敏样本` | 生产真实数据样本 | 机构书面批准；不得含真实身份可识别信息；用完登记处置方式 |

**禁用**：以生产库直接作为测试环境；以未批准的真实身份可识别数据作为测试数据；用有副作用的探针脚本代替用例。

### 7.3 执行记录最小字段

执行人、执行日期、环境标识、数据类别、用例号、实际结果、结论、偏差号、证据号。缺任一字段视为记录不完整，不能作为发布批准依据。

## 8 偏差、缺陷与变更处理

### 8.1 偏差（DEV）

偏差 = 用例未通过、判据未达成、或执行偏离本计划/方案。规则：

1. 失败用例**不得以"重跑通过"覆盖**：原结果保留，另开偏差单记录原因、处理与最终结论；
2. 每条偏差须有：级别（关键/重大/轻微）、对预期用途的影响评估、处理措施、复测结果、批准人；
3. 影响高风险面的偏差**未闭环即不得发布**；轻微偏差可带残余风险发布，但须写入 CSV-12 残余风险清单并给出后续处置时点；
4. 偏差级别由机构与我方共同判定，机构有最终裁定权；判级依据是"对数据完整性与受试者权益的影响"，不是"修复工作量"。

### 8.2 缺陷与问题登记（ISS）

上线后发现的系统问题进 CSV-14 台账，与系统内质控问题登记同口径；重复出现或成趋势的问题必须触发系统性原因评估（GCP 53(四)），并作为年度验证回顾的输入。

### 8.3 变更与再验证（CR）

| 变更类型 | 编号 | 再验证范围规则 |
|---|---|---|
| 配置变更（表单/清单/流程/政策键/模板/编号） | `CR-C-` | 受影响节点与表单回归 + RTM 增补；在途实例锁定版本不受影响须专项确认 |
| 版本升级（缺陷修复、新功能） | `CR-V-` | 高风险面全回归、中低风险抽样；触及 URS 时须机构批准需求修订 |
| 接口变更 | `CR-I-` | 集成验证四条标准全项重执行 |
| 基础架构变更 | `CR-A-` | IQ 重确认 + 备份恢复测试 |
| 法规适配变更 | `CR-R-` | 附录 A/B/C 符合性矩阵修订页 + 对应 URS 条目回归 |

四条纪律（与方案 6.6 一致）：① 已应用的数据库结构变更不可改写，后续变化以增量方式实施；② 节点级配置变更须覆盖该流程码的全部版本行，否则在途实例等不到补丁；③ 只在脚本里写、界面不暴露的字段会在下一次配置发布时被复原，此类字段必须两侧都有入口；④ 发布动作由机构授权人员在页面执行并留名，不允许以脚本代替机构批准。
