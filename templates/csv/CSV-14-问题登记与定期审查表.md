## 1 目的与范围

### 1.1 目的

规定系统运行期问题的**登记口径、分级判据、处理时限、升级路径与定期审查节奏**，使"问题被记录、被评估、被处置、被审查"四件事都有可交付的证据件；同时作为 CSV-15 年度验证回顾的直接输入件来源。

### 1.2 适用范围

| 适用 | 说明 |
|---|---|
| 生产环境全部运行期问题 | 不论来源（用户报障、验证遗留、检查发现、监控告警）一律进同一台账，不允许"IT 一本、质量一本" |
| 测试/预发环境问题的处置结论 | 环境内问题若影响生产可用性判断或暴露合规面缺陷，须登记；纯环境内的一次性调试不登记 |
| 与验证阶段偏差的衔接 | OQ/PQ 执行中发现的偏差（`DEV-`）在系统上线时未闭环的部分转入本台账，保留偏差号引用 |

### 1.3 不适用

配置、版本、接口、架构、法规五类**改动本身**走 CSV-13 建变更单；本台账记"发现的问题"。一个问题的处置若需要改系统，则派生一张变更单，两者互相引用（`ISS-` ↔ `CR-`），不可合一。

## 3 问题定义与来源

### 3.1 定义

**问题** = 系统的实际表现与其经批准的预期用途、配置取值、判据或服务质量约定之间的任何偏离，或虽未偏离但足以影响合规证据可及性的状况。

不视为问题的情形（走对应载体）：业务操作错误本身（走系统内更正流程）、人员不会用（走培训，CSV-11）、需要新能力（走需求与变更，CSV-13）。**但"操作错误频发"或"反复不会用"本身是问题**——它说明界面或培训未达预期用途。

### 3.2 六类来源（登记时必选其一）

| 来源 | 典型入口 | 与它物的关系 |
|---|---|---|
| S1 用户报障 | 帮助台/统一受理入口、域内关键用户上报 | 最常见来源；按第 6 章时限响应 |
| S2 验证偏差转入 | OQ/PQ/集成/性能执行中未闭环的 `DEV-` 项 | 保留偏差号，台账"来源"记 S2 |
| S3 质控检查发现 | 机构质控检查、项目质控活动中发现的系统相关问题 | 与系统内质控问题管理同台账口径（第 9 章映射） |
| S4 迎检发现 | 监督检查/申办方稽查现场提出的系统相关问题 | 一律关键或重大级起步，禁止归"观察" |
| S5 内部审计发现 | 机构质量管理内部审计、年度回顾中的抽查发现 | 结论落 CSV-15 |
| S6 监控与告警 | 巡检与健康检查（配置体检、待办积压、异常导出、慢查询、存储容量、备份作业状态）、时间源偏差告警、安全事件告警 | 上线初期巡检加密（每周），稳定后按月；发现即登记 |

## 4 问题分级

判级依据只有一个维度：**对数据完整性、试验参与者权益、合规证据可及性的影响**。修复工作量、沟通成本、谁提出的级别诉求都不构成判级依据。级别由受理人与机构组织管理部门共同判定，机构有最终裁定权。

| 级别 | 判据（满足其一即定该级，取最高适用级） | 处置要求 |
|---|---|---|
| **关键** | 存在试验参与者安全或权益受影响的可能；数据完整性受损或可能被质疑（记录不可追溯、前后值丢失、签名不可校验、编号出现重复、轨迹面被削弱）；系统整体不可用且无绕行；已签发出文书的真实性存疑；证据在迎检或法定时限内不可提供 | 立即启动应急（方案 12.3—12.7）；必要时按 CSV-13 第 8 章走紧急变更；同期评估是否构成方案偏离或需对外说明；闭环前每日复核 |
| **重大** | 关键流程受阻但有绕行（签署、递交、分派、发药核对、访视录入受阻）；闸口/权限/归档行为与批准取值不一致但未造成数据损失；在途实例锁定版本表现异常；出文模板取数错误尚未批量发生；权限或数据档位越界风险 | 在约定时限内闭环（第 6 章）；闭环前逐例记录绕行处置；须评估是否触发 CAPA 与再验证 |
| **一般** | 非关键功能异常、报表或列表口径显示问题、提示语误导但不影响判定、导出格式问题、单点性能缓慢 | 纳入处置队列；累计影响同类判据时按第 8 章升级 |
| **观察** | 体验优化、文案与版式建议、无合规影响的增强诉求 | 可纳入版本计划；不得以此级别收纳 S4 迎检发现与任何涉及闸口/轨迹/签名的现象 |

**分级红线**：任何涉及权限闸、稽查轨迹、电子签名、材料封口与归档只读、流程推进闸、编号唯一性的现象，最低定为重大级，不得为赶进度或减少台账压力降为一般/观察。

## 5 登记字段与填写规则

| 字段 | 填写规则 |
|---|---|
| 问题号 | `ISS-<年>-<序>`，年度内顺序号，一经分配不复用、不回收 |
| 来源 | S1—S6 之一（第 3.2 章） |
| 发现日期 / 登记日期 | 两者分开记；发现日期以事实发生时点为准，不以建单时点冒充 |
| 报告人 / 受理人 | 姓名与岗位；报告人为试验参与者本人或其家属转达时，只记转达渠道，不记个人可识别信息 |
| 环境 | 生产 / 预发 / 测试；生产须写实例标识，使证据可回放 |
| 影响对象 | 业务域、页面或功能、涉及的流程环节与节点、受影响单据范围（项目/单据的数量与标识按受控名单单独保存，台账内只写范围描述） |
| 现象描述 | 可被第三人复现的客观描述：操作路径 → 预期 → 实际；禁写结论性判断 |
| 是否涉及数据完整性 | 是/否 + 依据。判据：是否影响记录的可追溯性、归属、时间真实性、前后值捕获、签名有效性、编号唯一性。答"是"即最低重大级并要求影响排查 |
| 级别 | 关键 / 重大 / 一般 / 观察（第 4 章） |
| 根因分类 | 配置 / 缺陷 / 使用 / 外部依赖 / 数据 / 需求本身有误（六选一或多，主因置前）。"使用"类须继续回答"为什么会被误用"，界面或培训缺陷归此因 |
| 临时措施 | 在正式处置前的绕行、纸质降级或人工核对方式；纸质降级件须现场签名与时间、不得倒签；补录须标注"离线期间发生、恢复后录入" |
| 纠正措施 / 预防措施 | 纠正 = 消除已发生问题的原因；预防 = 防止再发生或扩散（可含配置补强、用例新增、培训、提示语调整）。涉及系统改动时派生 `CR-`，此处只写引用号 |
| 是否触发 CAPA | 是/否 + 依据；为"是"时记 CAPA 编号（第 9 章映射） |
| 再验证范围 | 引用的用例编号或"无需再验证 + 依据"（依 CSV-13 第 6 章决策表判定） |
| 验证与关闭 | 处置后由**非处置人**验证效果：验证人/日期/结论；关闭须同时满足"根因已消除 + 效果已验证 + 影响单据已核对" |
| 残余风险 | 未能完全消除的部分 + 后续处置时点 + 责任人；写入 CSV-15 第 6 章残余风险清单 |
| 关联号 | `DEV-`、`CR-`、CAPA 号、`EV-` 号列表 |
| 状态 | 已登记 / 处置中 / 待验证 / 已关闭 / 已作废（作废保留行并注明原因） |

**填写纪律**：① 现象与结论分开写，禁止用"已知问题"糊弄；② 空缺即不完整，不完整记录不能作为年度回顾输入；③ 关闭后发现问题未真正消除，不重开原单，另建新单并在关联号回指原单（保持时间线真实）。

## 6 处理时限与升级路径

### 6.1 时限表（分角色）

下列时长为**待机构与信息科确认的填写位**：本文件不预设数字，档位口径候选见方案 11.2（响应与处置分级），最终以双方 SLA 约定为准并回填本表；回填后视为经批准的判据，改动须走 `CR-`。

| 级别 | 受理确认 | 首次响应（判定并给出处置方向） | 临时措施就位 | 根因分析与处置方案 | 闭环（含效果验证） | 复核节奏 |
|---|---|---|---|---|---|---|
| 关键 | 〔待填〕 | 〔待填〕 | 〔待填〕 | 〔待填〕 | 〔待填〕 | 每〔待填〕小时一次，直至恢复 |
| 重大 | 〔待填〕 | 〔待填〕 | 〔待填〕 | 〔待填〕 | 〔待填〕 | 每工作日一次 |
| 一般 | 〔待填〕 | 〔待填〕 | N/A（无绕行需求时显式写明） | 〔待填〕 | 〔待填〕 | 月度例会清点 |
| 观察 | 〔待填〕 | 〔待填〕 | N/A | 纳入版本计划〔待填〕 | 〔待填〕 | 季度清点 |

责任分工：**受理与登记** = 机构指定受理人；**首次响应与根因** = 我方（配置/使用类由机构侧主导）；**临时措施与业务影响排查** = 机构受影响业务域；**效果验证与关闭** = 机构受理人指定的非处置人；**超期升级** = 受理人发起。

### 6.2 升级路径

| 触发 | 升级到 | 动作 |
|---|---|---|
| 超时限未响应或未闭环 | 机构组织管理部门负责人 + 我方项目经理 | 台账记"超期"并写原因；列入月度运营例会必看项 |
| 关键级且影响在途试验参与者安全或法定时限 | 机构组织管理部门负责人与信息科负责人同时知会 | 启动应急与降级方案（方案 12.7），必要时按 CSV-13 第 8 章走紧急变更 |
| 涉及数据完整性且无法证明影响边界 | 机构质量管理层面 | 评估是否构成方案偏离及对外说明义务（按机构制度与 GCP 要求处理） |
| 根因指向需求本身有误 | 回到 CSV-02 走 URS 修订 | 以 `CR-R`/`CR-C` 承载，禁止"改判据迁就结果" |
| 同类问题重复达第 8 章阈值 | CAPA 与再验证评估 | 强制升级，不得以"已逐条修复"结案 |
| 迎检现场提出的系统问题 | 直接关键/重大级 | 当场记录、当场指定责任人、事后补全字段 |

## 7 定期审查

四类审查构成"定期审查系统运行情况"的完整答复，节奏由机构批准并写入本表；每次审查的**输入件、抽样方法、结论落点**三件齐备才算完成，缺任一件按未完成记入年度回顾。

| 审查 | 频率 | 主持 | 输入件 | 抽样/检查方法 | 结论落点 |
|---|---|---|---|---|---|
| **A 月度运营例会** | 每月〔待填〕日 | 机构受理人，我方参加 | 本月新增与在办问题清单、超期项、S6 巡检与健康检查输出、待办积压与异常导出、慢查询与存储容量观察 | 全量清点（不抽样）：逐条看状态推进与级别是否恰当；对重复现象当场标注关联号 | 会议纪要 + 台账"级别复核"更新；纪要归档为 `EV-`；构成 ★A1.8 的直接证据 |
| **B 季度权限审查** | 每季度一次〔待填〕月 | 机构组织管理部门 + 信息科 | 用户管理导出的账号—角色—机构归属清单、角色权限页的码—角色映射、数据范围矩阵页当前取值、系统资源台账页的写接口鉴权覆盖数字、上季度入职/离职/轮转名单（受控名单单独保存） | ① 账号与在岗名单双向核对：有账号无人、有人无账号、离职/轮转未停权逐条点名；② 权限码与角色授权与批准基线比对；③ 数据档位取值与出厂矩阵差异核对；④ 写接口鉴权覆盖静态对账（输出为空或计数为 0 时先确认脚本未中途抛错）；⑤ 迎检临时授权是否全部到期撤销 | 审查记录表（第 11 章模板）+ 整改项进台账并派生 `CR-`（涉及定义改动时）；季度结果汇总进 CSV-15 第 4 章③ |
| **C 半年签名与轨迹抽检** | 每半年一次〔待填〕月 | 信息科 + 机构质量管理 | 稽查轨迹导出件、签名记录与校验能力、备份与恢复演练记录、时间源偏差巡检记录 | 随机抽取已签署记录 N 条（N 由机构确定并填〔待填〕）逐条重算内容哈希并核对绑定关系；抽取修改类轨迹 M 条核对前后值捕获与人员/时间归属；核对轨迹关闭开关在配置面不存在 | 抽检记录表 + 校验输出件入 `EV-`；不一致即定关键/重大级并启动影响排查；结果进 CSV-15 第 4 章⑤ |
| **D 年度验证回顾** | 每年一次，与年度质量管理评估同期 | 机构组织管理部门批准、我方编制 | 见 CSV-15 第 3 章输入件清单（含本台账） | 全年度汇总 + 趋势分析 + 抽样复核 | CSV-15 报告与结论三档判定 |

**审查纪律**：① 审查发现问题**必须先登记再整改**，禁止"改了就算审查通过"；② 审查结论只认记录与导出件，不认口头说明；③ 审查人不得同时是被审查对象的处置人本人。

## 8 系统性问题识别规则

出现下列任一情形即判定"可能为系统性问题"，强制触发 CAPA 评估与再验证范围评估（CSV-13 第 6 章），不得以单条修复结案：

| 规则 | 判据（阈值为机构确认位） |
|---|---|
| 重复 | 同类问题（同根因分类 + 同现象类别）在连续〔待填〕个月内累计达〔待填〕次 |
| 集中 | 同一模块/流程域在〔待填〕个季度内问题占比集中出现（观察性判断，不设百分比门槛，由审查会集体裁定） |
| 跨模块同因 | 同一根因分类在〔待填〕个及以上模块分别引发问题 |
| 闸口类必升 | 涉及权限闸、轨迹、签名、封口与归档只读、推进闸、编号唯一性的问题，无论次数，一次即评估是否系统性 |
| 数据完整性 | 任一条答"涉及数据完整性 = 是"的问题，除闭环外须评估同因是否存在于其他对象（横向排查记录为必填写入） |
| 验证穿透 | 问题现象本应由已通过的 OQ/PQ 用例捕获 → 说明用例集存在缺口，须补用例并回改 CSV-07/CSV-09 与 RTM |

**处置动作固定四件**：横向排查（同因还有谁）→ 根因消除（配置/缺陷/培训/需求）→ 用例与 RTM 增补 → 效果验证与非处置人关闭确认。四件缺一即不得写"已关闭"。

## 9 与系统内质控问题登记 / CAPA 的对应关系

避免"IT 台账与质量台账各记一套"，两套记录的分工与映射如下。

| 台账 | 系统内页面出口 | 装什么 | 编号映射 |
|---|---|---|---|
| 质控问题管理 | 质控问题管理页（列表可按项目、来源、级别筛选并导出） | **业务对象**的问题：项目质控、监查、稽查发现，以及由系统问题引起的业务影响在质量侧的处置记录 | 系统内问题记录号 ↔ `ISS-<年>-<序>`；同一事实两边各一行时，须在关联号字段互相引用，不重复描述 |
| CAPA | 质量管理 → CAPA（纠正与预防措施，含整改提交与验证环节） | 需要**根因消除与效果验证闭环**的合规风险处置；由系统问题引起的合规风险一律走此路 | CAPA 编号记入 `ISS-` 的"是否触发 CAPA"字段；CAPA 侧记 `ISS-` 号回指 |
| 缺陷管理 | 质量管理 → 缺陷管理 | 已确认为产品缺陷、需在版本计划内修复的条目 | 缺陷条目 ↔ `ISS-`；修复发布走 `CR-V-`，再验证结果挂回两者 |
| 稽查轨迹 / 系统资源台账 / 配置体检器 | 系统管理各页与配置体检器页 | 审查输入件的可再生来源（导出件、覆盖数字、配置对账） | 导出件登记为 `EV-`，在审查记录表引用 |

**四条映射纪律**：
1. 一张 `ISS-` 只对应一个"事实"，质量侧与系统侧分别记录处置视角，两边都不许单独宣称结案。
2. 编号互指不互抄：不把系统内自动生成的记录号当作 `ISS-` 号使用，也不反向替换。
3. 导出件优先：审查证据以页面导出件形态入 `EV-` 台账，避免截图。
4. 敏感面隔离：涉及人员身份与联系方式的名单不进导出件正文，另以受控名单附件保存并在台账注明存放位置。
