## 1. 范围与非目标
- 每个项目维护功能点、R0–R4 用例基线、逐轮记录和报告；复用现有用例库，人工新增与改版。

## 3. 流程规则
1. **用例与批准**：保留现有实现：新建 `current_version=1` 并同 batch 插首版；每次编辑在同 batch 更新用例并追加版本行，新增服务端及页面非空 `change_summary` 校验；`expected !== current_version` 返回 409。现状摘要可空，必填为本期补强。
2. **批准真源**：沿用 `test_cases.status(draft/approved)` 与 `approved_by/approved_at`；编辑已批准用例回 draft 并清批准信息；不新增版本级 state。用例批准与基线冻结是两层独立审批。
3. **基线**：仅将当前已批准用例纳入，原子读取并锁定来源 tc_version 和完整快照；冻结后不可修改，只能新建 revision。页面显示 `<发布版本号> · 基线 rev<N>`，无 release_id 显示 `通用 · 基线 rev<N>`；专用基线只用于所属发布版本。
4. **开轮与执行**：预填该发布版本最新冻结基线，无则回退通用冻结基线；维护者必须显式确认后创建。执行只读关联基线项的冻结快照，不读当前用例；同一发布版本重跑新增轮，不覆盖原结果。
5. **三态与对比**：记录 PASS/FAIL/DIFF，DIFF 填原因并由账号确认，未签或拒签按 FAIL，获批单列；未执行项阻止关轮。显式选同项目两轮，按 tc_id 配对；snapshot_hash、manifest_hash 相等且环境/配置一致才可比。
6. **对比结果**：旧非失败→失败为新失败，失败→失败为老失败，失败→PASS 为已修复，失败→获批 DIFF 为差异获批；预期变更或其他不满足门槛项列“不可比/预期变更”，不计回归失败。
- 用例编辑留痕由版本表及 change_summary 承担，继续与用例更新同 batch 写入；regression_events 只记回归侧操作，不要求用例编辑另写审计事件。
- TC 继续使用 counters.tc_code 原子递增，`TC-` 加至少三位数字补零，全局唯一不复用；FP 编号项目内唯一。功能点映射或断言意图变化时新建用例、退役旧条，不硬删历史。
- 迁移前备份和演练；保留旧 ID、tc_version NULL 与 deviation 原义，旧执行标 legacy 只读；重建执行唯一约束后对账，不通过恢复备份。
- 报告在关轮后生成存储型快照，批准冻结后不可修改，更正建 revision；支持页面、JSON 和浏览器打印 PDF。

## 6. 验收标准
1. 维护者切换项目只看到本项目资产，跨项目读取报告或创建基线、映射、轮次时被拒绝。
2. 两项目并发创建用例时得到不同且全局递增的 TC 号；计数器缺失时取号失败，已分配号码不复用。
3. 新建用例后看到 current_version=1 和首版；编辑提供非空摘要后看到新增版本；空摘要被拒绝，旧数据保持原样。
4. 两人同时编辑同一版本时，后提交的过期 expected_version 请求得到 409，版本行和当前内容不被覆盖。
5. 已批准用例编辑后看到状态回 draft、批准人时间清空；重新批准后看到批准人时间；基线冻结独立于此。
6. 维护者冻结基线后编辑源用例，轮次仍使用原快照；快照能还原 title/risk/ctype/related_req/covers_urs、步骤与功能点映射。
7. 维护者修改已冻结基线或未显式确认基线便开轮时被拒绝；同一发布版本两轮各自绑定基线项，第二轮不覆盖第一轮。
8. 测试者记录 DIFF 时未签/拒签计为 FAIL；确认接受后看到差异获批，原始结果仍为 DIFF。
9. 评审者对比已关闭轮次时看到新失败、老失败、已修复、差异获批与不可比；预期变更归“不可比/预期变更”，不误判回归失败。
10. 维护者查看旧执行时看到 legacy、原 deviation 和未知版本标记；NULL tc_version 不回填且旧记录不可覆盖。
