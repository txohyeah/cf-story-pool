## 2. 设计原则

1. **pool 管流转与台账，不管文档全文**：CSV 正式文档（URS/OQ/验证报告）仍由 AI 照模板在工作区生成归档，pool 只存单据与编号引用——D1 容量与工具定位都不适合承载文档全文
2. **编号互指，不互抄**：pool #N 与合规编号（`ISS-2026-001`、`CR-V-2026-001`）双向可查，谁也不替代谁
3. **先轻后重**：能用标签+字段表达的先不加实体（CR 变更单先轻做，跑一版再决定是否实体化）
4. **be-trial 是配置不是特例**：所有新功能按"项目"维度隔离，be-trial 的标签体系/编号规则/状态映射作为项目级配置，oncology 上线=复制配置

## 3. 功能清单（分期）

### 3.1 P0：单据模型增强（bug/偏差台账对齐 CSV-14）

- `type` 字典扩展：`req`（需求，已有）/ `bug`（缺陷）/ `dev`（验证期偏差）——实操确认 type 是否自由字典，不行用标签
- 新增字段（requirements 表 ALTER）：
  - `severity`：关键/重大/一般/观察（四级，CSV-14 口径；涉及权限/轨迹/编号/更正留痕最低"重大"——前端提示，不做硬校验）
  - `root_cause`：配置/缺陷/使用/外部依赖/数据/需求有误（六选一，可空）
  - `ref_code`：合规编号引用（如 `ISS-2026-001`），编号直达搜索同时匹配此字段
  - `related_codes`：关联号列表（DEV-/CR-/TC-/EV- 互指）
- 状态机不变（submitted→confirmed→scheduled→fixed→verified→closed）；流程约定固化进 PRD：**关闭须非处置人确认**（我处置→用户确认关闭）
- 工作量：schema 增量 + 表单/详情页字段 + 列表筛选列 ≈ 1-2 晚

### 3.2 P0：CR-V 版本发布单（轻做）

- 不新建实体：**版本发布=一条 type=`bug`/`req` 批次关联的单据**太绕，直接做法：新建 `releases` 表（轻量 5 字段：id/project/version/release_date/change_scope/retest_scope + 状态）
- 或更轻：版本发布用**标签**（`v1.5`）+ 把当版修复的 bug 单据都挂该标签，CR 编号写在项目描述里
- **推荐：先建 `releases` 轻表**（版本是导出与追溯的高频维度，标签承载不了"再验证范围/发布确认人"这些字段）；跑一版后视需要升级为完整 CR 实体
- 工作量：≈1 晚

### 3.3 P0：筛选导出（用户点名，最高优先）

- 按项目+标签+状态+类型筛选导出 CSV/Excel：编号/标题/类型/状态/severity/根因/提单人/日期/ref_code
- 按 CSV-14 统计口径出五维度汇总（来源/级别/根因分类/业务域/状态）
- 实现纯 worker 端（查询已有，拼 CSV 响应流），前端导出按钮；**不需要 JS Excel 库，CSV 直接给**
- 工作量：≈1 晚

### 3.4 P1：定期审查留痕

- 月度运营例会：导出当月清单（§3.3）→ 审查结论以**评论+标签（`月度审查-YYYYMM`）**留痕在 pool 或建一条"审查记录"单据
- 不新建实体，复用现有单据+评论机制
- 工作量：≈0.5 晚（主要是约定）

### 3.5 P1：文档生成脚本固化（pool 数据 → CSV 文档）

- `scripts/docgen.py` 入库：从 pool API 导出结构化数据 → 填充 `templates/` 下的文档骨架 → 产出：
  - CSV-14 问题登记表（md/docx）
  - 版本测试报告草稿（md，AI 润色后定稿）
  - RTM 需求溯源片段
- 模板来源：`/tmp/ctms-ref/` 15 件套骨架入库到 `projects/cf-story-pool/templates/csv/`（md 版）
- 生成动作由 AI 执行（跑脚本+润色），产物归档到目标项目目录（如 `projects/be-trial/be-trial-verification-docs/csv/`），可选作为附件挂回 pool 单据
- 这是"固化"的核心：以后 oncology 出同类文档 = 换项目参数跑同一脚本
- 工作量：≈2 晚

### 3.6 P2（观察项，暂不做）

- worker 内置模板导出（在线一键下载 docx）：等 §3.5 跑顺、确有高频需求再上
- 完整 CR 实体（八步流程状态机）：等轻量版跑一版再决定
- TC 用例库进 pool：**不做**（用例全文留 CSV 文档，pool 只引用 TC 编号）

## 4. be-trial 落地配置（第一个实例）

- 项目字典：`be-trial`（已有）
- 编号映射：pool #N ↔ `ISS-<年>-<序>`（ref_code 字段双向）
- 标签体系：版本标签（v1.5…）+ 端标签（PC端/PDA端）+ 性质标签（沿用现状）
- 三件套互指流程：UAT 发现问题 → pool 建单（channel=agent）→ CSV-14 登记 ISS → 修复版本登记 releases/CR-V → 复测闭环 verified
- 详细操作口径见 `projects/be-trial/be-trial-verification-docs/00-版本测试管理规划.md`（该文档管"be-trial 怎么执行"，本文档管"pool 系统建什么"）

## 5. 开发顺序建议

1. **§3.3 导出**（用户点名+价值最直接）
2. **§3.1 单据字段增强**（分级/根因/关联号——为导出和文档生成供数）
3. **§3.2 releases 轻表**
4. **§3.5 docgen 脚本+模板入库**（不依赖前面完成，可并行）
5. §3.4 审查留痕（纯约定）

## 6. 边界（明确不做）

- CSV 正式文档全文进 D1（体积+归档合规都不合适）
- TC 用例库全文管理
- 电子签名/审批流（签署仍走 CSV 文档签名页线下签署）
- 稽查轨迹合规化改造（pool 自身 events 流水够内部追溯用；GxP 稽查轨迹是 be-trial 本体的义务）
